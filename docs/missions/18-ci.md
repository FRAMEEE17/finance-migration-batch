## Exploration

Two real bugs found by actually running the fixture through the real
pipeline, not by reading the SQL and reasoning about it:

- **`reconcile_mismatch.py` crashes on a truly fresh warehouse.**
  Reproduced with zero fixture code involved, isolated
  `/tmp/truly-fresh-test.duckdb`: `reconcile_mismatch.py` LEFT JOINs
  `recon_reversal_pairs`, which only `reconcile_reversals.py` creates,
  and `docs/runbook.md`'s documented sequence never mentions that
  script. `scrutinize`d before fixing: the tempting fix (a defensive
  stub table inside `reconcile_mismatch.py`) would silently degrade
  every `recon_mismatch` row's pair enrichment to permanent NULL
  instead of loudly failing - worse than the crash, not better.
  Real fix: add the missing step to `docs/runbook.md` and to
  `tests/ci_checks.py`'s pipeline. Verified against the real dataset
  afterward: `recon_reversal_pairs` rebuilds to exactly 1,025 pairs,
  `recon_mismatch` to exactly 219 rows (17+200+2) - the already-known
  P01 anchor, unchanged.
- **The fixture parquet's all-`None` columns got the wrong type.**
  `reference`/`header_text`/etc. are legitimately null on every fixture
  row; pandas/pyarrow inferred one of them as `INTEGER` with nothing
  else in the column to hint otherwise, and DuckDB's own VARCHAR-typed
  real schema then rejected it (`~~(INTEGER, STRING_LITERAL)` on a
  `LIKE` comparison). Fixed by building the fixture from an explicit
  DuckDB `CREATE TABLE` schema (copied from `DESCRIBE` against the real
  file) instead of relying on pandas type inference - confirmed
  column-for-column, name and type both, identical to the real source.
- **A third finding, real but out of scope**: the fixture's deliberately
  unmapped account (`999888`, absent from `map_account.csv` entirely)
  never gets flagged by `quality_gate.py`'s `unmapped_account` check,
  even though `docs/definitions.md:200` documents that exact case as
  in scope. `build_mapping.py` guarantees the real dataset structurally
  can't produce this case (every account in scope always gets a row),
  so 16 tickets of real data never exercised it. Filed as issue #17,
  not fixed here - the blast radius (does this affect real P01-P03
  data today, does fixing it change `dq_violations` counts everywhere)
  is bigger than a CI ticket should absorb. `tests/ci_checks.py` pins
  today's actual (gap) behavior, not the documented one, so a real fix
  is a deliberate, visible change to that one check.

## Retro

Two real production bugs surfaced by a tiny, synthetic, 15-row fixture
that 16 tickets of real 649k-row data never triggered - both because
the real data structurally can't produce the conditions that expose
them (a truly fresh warehouse missing `recon_reversal_pairs`; a
`gl_account` genuinely absent from `map_account.csv`). Neither is a
fixture-testing artifact; both were reproduced independently against
real, isolated warehouses with zero fixture code involved, before
being trusted. That's the actual case for CI here beyond "merge
gating" - it's the first thing in this project that ever ran the
pipeline from true zero instead of against the same warehouse file
that's accumulated state since ticket 2.

Every assertion in `tests/ci_checks.py` got corrected at least once
after actually running it, not left as a first-draft guess: the
duplicate-grain check's comment claimed the document's other line
would still load, and it didn't (a real, explicable side effect of
duplicating a line also doubling it in the balance sum) - fixed by
checking, not by re-deriving the "right" answer from reading the SQL
harder. The unmapped-account check similarly started as an assumption
("this should get flagged") that turned out false against real
behavior - reframed as a pinned known-gap once the actual cause was
traced (issue #17), not forced to pass by picking an easier test case.

Branch protection is the one item this mission can't close by itself -
GitHub's own platform rejects it on a private repo without a paid
plan. Recorded as blocked, not silently downgraded to "done in spirit"
or worked around with something that only looks equivalent (a
pre-commit hook, say, which a `--no-verify` push defeats trivially).

Scope discipline held on the two real findings that came up but
weren't this ticket's job: `reconcile_reversals.py`'s hardcoded
company/year/period constants (inconsistent with every other script's
ticket-10 parameterization) and the `unmapped_account` gap itself both
got named and left alone, not folded in because they were sitting
right there mid-trace.
