# Mission 10: Backfill 2024-02 and 2024-03

- **Signal:** issue #10, blocked by #9 (closed).
- **Confidence:** high on the mechanics (no new mapping gaps, no
  unbalanced documents, no new document-boundary types to design
  around). Medium on scope, because every script from #4 through #9 was
  built hardcoded to P01 specifically, not written to take a period as
  an argument - that refactor is this mission's real work, not "run the
  same script again."
- **Type:** request with a refactor underneath it. "Load P02/P03 with
  the same loader" only works if the loader (and the 4 scripts
  downstream of it) can take a period as an input instead of a constant.
- **Decision:** act. Parameterize `src/load_fact.py`,
  `src/reconcile_account.py`, `src/reconcile_mismatch.py`,
  `src/build_period_report.py` by period. Load P02 and P03. Prove P01's
  own numbers don't move. Escalate the local_amount finding's real
  scope, since it turns out not to be P01-specific.

## Rules that apply

> "Load (2024, 02) and (2024, 03) with the same loader, and prove
> (2024, 01) didn't move." (issue #10)

> "**Period load:** replacing a period replaces the **whole** period,
> never append. Re-running with unchanged mapping must yield the same
> totals and row counts." (docs/business-rules.md)

> mission 04: "delete this period's rows, insert it again, one
> transaction" - already scoped per-period at the SQL level
> (`DELETE FROM fact_gl_line WHERE {PERIOD_FILTER}`), the constraint is
> that `PERIOD_FILTER` itself was a fixed module constant, not a
> parameter.

## Exploration

`notebooks/10-backfill-2024-02-03.ipynb`.

- **P02**: 13,723 rows / 3,713 documents. **P03**: 13,521 rows / 3,708
  documents. Both close in size to P01's 13,142 rows.
- **`map_account.csv` already covers both periods completely** (0
  accounts missing from either). Ticket 3's mapping scope was always
  P01-P03, not just P01 - no new mapping work needed.
- **0 unbalanced documents in either period** (P01 had exactly 1). No
  `OPENING_BALANCE`/`CL` documents in P02 or P03 (expected - brought-
  forward balances land at fiscal-year start, not mid-year).
  `is_post_close` still fires normally (62 in P02, 101 in P03).
- **The `local_amount` defect (issue #13) is not P01-specific, and it
  gets worse.** P01: 20 documents / 97,144,587.1. P02: 27 documents /
  104,111,412.57. P03: 36 documents / 340,498,930.13. Same signature
  each time (checked the top 3 offenders per period): unusually high
  line counts, a document total broadcast across every debit line. This
  changes #13's scope from "a P01 finding" to "a pattern across the
  whole dataset" - worth updating that issue once this mission lands.
- **Structural risk found while reading the existing code, not from
  data**: `src/reconcile_account.py` and `src/reconcile_mismatch.py`
  both use `CREATE OR REPLACE TABLE`, a full rebuild, driven by a single
  hardcoded `PERIOD_FILTER`. Naively re-pointing that constant at P02
  and re-running would silently wipe P01's already-signed-off rows out
  of `recon_period_summary`/`recon_mismatch`, not just add P02's. This
  is the actual reason issue #10 asks to "prove P01 didn't move" - the
  risk is real, not a formality.

## Desired outcomes

- `src/load_fact.py`: `load_period(con, company_code, fiscal_year,
  fiscal_period)` takes the period as arguments; `main()` loads a list
  of periods (P01, P02, P03) in one run, each through its own delete-
  then-insert transaction, unchanged per-period behavior from mission 04.
- `src/reconcile_account.py` / `src/reconcile_mismatch.py`: rebuilt to
  iterate every period actually present in `fact_gl_line` (queried, not
  hardcoded), so adding P02/P03 extends the table instead of replacing
  it, and P01's rows regenerate identically alongside the new periods
  rather than needing to be preserved by omission.
- `src/build_period_report.py`: takes a period, writes
  `reports/period_2024-02.md` and `reports/period_2024-03.md` using the
  same split sign-off pattern mission 09 established (`Reconciliation:
  accepted` / `Reported local_amount total: not signed`), each with its
  own period's dollar figures, not P01's copied over.
- A captured before/after snapshot proving P01 unchanged: row count,
  distinct document count, `SUM(local_amount)` for P01's `fact_gl_line`
  slice, identical before this mission's backfill and after.
- Issue #13 updated with the 3-period scope finding.

## Deterministic checks

- [ ] P01's `fact_gl_line` row count, document count, and
      `SUM(local_amount)` are byte-identical before and after the P02/P03
      backfill (the actual "prove P01 didn't move" proof, not a claim).
- [ ] P02 and P03 each load through the same blocking/non-blocking gate
      as P01 (`dq_violations` gets real rows for both periods, checked
      by check_name, not assumed empty).
- [ ] `recon_period_summary` and `recon_mismatch` contain P01, P02, and
      P03 rows simultaneously after this mission, not just the most
      recently built period.
- [ ] `reports/period_2024-02.md` and `reports/period_2024-03.md` exist,
      each with their own period's local_amount defect figures (104M/27
      docs and 340M/36 docs respectively), not P01's numbers reused.
- [ ] Re-running the full backfill (all 3 periods) twice gives identical
      `fact_gl_line`, `recon_period_summary`, and `recon_mismatch`
      contents.
- [ ] `src/checks.py`'s existing P01-anchored checks (row counts, known
      mismatch counts, etc.) still pass unmodified after this mission,
      proving the refactor didn't change P01's own numbers as a side
      effect of generalizing the code.
