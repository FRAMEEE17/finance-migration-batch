# Mission 10: Backfill 2024-02 and 2024-03

- **Signal:** issue #10, blocked by #9 (closed).
- **Confidence:** high on the mechanics (no new mapping gaps, no
  unbalanced documents, no new document-boundary types to design
  around). Medium on scope, because every script from #4 through #9 was
  built hardcoded to P01 specifically, not written to take a period as
  an argument - that refactor is this mission's real work, not "run the
  same script again."
- **Type:** request with a refactor underneath it. "Load P02/P03 with
  the same loader" only works if the loader (and the 4 scripts
  downstream of it) can take a period as an input instead of a constant.
- **Decision:** act. Parameterize `src/load_fact.py`,
  `src/reconcile_account.py`, `src/reconcile_mismatch.py`,
  `src/build_period_report.py` by period. Load P02 and P03. Prove P01's
  own numbers don't move. Escalate the local_amount finding's real
  scope, since it turns out not to be P01-specific.

## Rules that apply

> "Load (2024, 02) and (2024, 03) with the same loader, and prove
> (2024, 01) didn't move." (issue #10)

> "**Period load:** replacing a period replaces the **whole** period,
> never append. Re-running with unchanged mapping must yield the same
> totals and row counts." (docs/business-rules.md)

> mission 04: "delete this period's rows, insert it again, one
> transaction" - already scoped per-period at the SQL level
> (`DELETE FROM fact_gl_line WHERE {PERIOD_FILTER}`), the constraint is
> that `PERIOD_FILTER` itself was a fixed module constant, not a
> parameter.

## Exploration

`notebooks/10-backfill-2024-02-03.ipynb`.

- **P02**: 13,723 rows / 3,713 documents. **P03**: 13,521 rows / 3,708
  documents. Both close in size to P01's 13,142 rows.
- **`map_account.csv` already covers both periods completely** (0
  accounts missing from either). Ticket 3's mapping scope was always
  P01-P03, not just P01 - no new mapping work needed.
- **0 unbalanced documents in either period** (P01 had exactly 1). No
  `OPENING_BALANCE`/`CL` documents in P02 or P03 (expected - brought-
  forward balances land at fiscal-year start, not mid-year).
  `is_post_close` still fires normally (62 in P02, 101 in P03).
- **The `local_amount` defect (issue #13) is not P01-specific, and it
  gets worse.** P01: 20 documents / 97,144,587.1. P02: 27 documents /
  104,111,412.57. P03: 36 documents / 340,498,930.13. Same signature
  each time (checked the top 3 offenders per period): unusually high
  line counts, a document total broadcast across every debit line. This
  changes #13's scope from "a P01 finding" to "a pattern across the
  whole dataset" - worth updating that issue once this mission lands.
- **Structural risk found while reading the existing code, not from
  data**: `src/reconcile_account.py` and `src/reconcile_mismatch.py`
  both use `CREATE OR REPLACE TABLE`, a full rebuild, driven by a single
  hardcoded `PERIOD_FILTER`. Naively re-pointing that constant at P02
  and re-running would silently wipe P01's already-signed-off rows out
  of `recon_period_summary`/`recon_mismatch`, not just add P02's. This
  is the actual reason issue #10 asks to "prove P01 didn't move" - the
  risk is real, not a formality.

## Retro

Parameterizing the 4 scripts went cleanly, `src/quality_gate.py` needed
zero changes since `run_gate(con, scope_filter)` already took its scope
as an argument from mission 05 - only the 4 scripts built directly
against a hardcoded period constant needed the refactor.

Two real bugs came out of the multi-period run, not from reading the
code in isolation:

- **SQL operator precedence.** `_periods_sql()`'s OR-chain, when
  concatenated with `AND NOT is_opening_balance AND ...` in
  `reconcile_mismatch.py`'s close-eligible CTE, only applied the NOT
  conditions to the last OR-ed period - AND binds tighter than OR. P01's
  opening_balance/post_close rows and all of P02 silently dropped out of
  `recon_mismatch` on the first run. Fixed by wrapping `_periods_sql()`'s
  output in an outer paren so it's always a self-contained expression.
- **Floating-point negative zero in report text.** DuckDB's parallel
  `SUM` isn't associativity-safe: the same debit/credit gap query
  returned a tiny negative float instead of exactly 0.0 depending on
  thread scheduling, which `ROUND(...,2)` turned into `-0.00` in the
  rendered report - same number, wrong sign, and non-deterministic
  across runs of the identical query. Caught by the
  `period_report_idempotent_rebuild` check once it started looping over
  all 3 periods instead of just P01 (P01's own gap happens to be exactly
  90.00, nowhere near zero, so it never triggered this). Fixed with a
  `_no_neg_zero()` normalizer applied to every rounded float before it
  reaches report text.

`load_fact.py` no longer has a default period - a call with nothing
specified fails with a usage message instead of quietly loading P01,
per the ticket 10 ruling. This is a breaking change for anything that
imported the old `PERIOD_FILTER` / `COMPANY_CODE` / `FISCAL_YEAR` /
`FISCAL_PERIOD` module constants - `src/checks.py` had roughly a dozen
functions built against those constants or against exact P01-only row
counts that silently stop being true once `fact_gl_line` holds 3
periods instead of 1. Fixed each one by either scoping it explicitly to
P01 (where the check's own claim is genuinely P01-specific, e.g. the
one known unbalanced document) or widening it to the full 3-period
scope (where the claim was always meant to hold across the whole
table). Same pattern for `build_period_report.py`'s checks, which now
loop over all 3 reports instead of reading one hardcoded path.

`recon_period_summary.imbalanced_local_amount` sums every
`local_amount_imbalance`-flagged document (23 in P01), not the
materiality-filtered 20 the report's own "Known issue" section quotes -
those are two different numbers built from the same underlying flag,
one unscoped and one filtered at >0.01. The gap between them is 3
sub-cent documents, small enough to stay inside the existing 0.5
tolerance on `recon_imbalanced_total_matches_known_finding`, but it's
worth a named ticket eventually so the two figures don't drift apart
silently as more periods get added.
